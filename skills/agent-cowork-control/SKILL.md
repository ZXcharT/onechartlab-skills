# Agent Cowork Control

主代理统一负责，子代理按功能协作。

## 什么时候使用，以及如何加载规则

先判断这项工作是否真的需要多个 Agent。资料来源多、步骤多或文件多，本身都不是分工理由：

- **轻量协作**：工作能自然分成两个以上互不重复的部分，分开处理可以并行推进、利用不同专长，或让另一个助手从不同角度核查。开始前提交简短的“步骤 → 验证”计划并获得用户确认；任务说明只需写清目标、每个助手负责什么、可以使用哪些来源、需要返回什么以及做到哪里停止。不需要独立 Plan 审查、Canary、运行目录、`FINAL.md` 或完整审核流程。
- **受控协作**：已经确认值得分工，而且还涉及方向或关键定义、计算方式的选择，高风险或难回退操作，需要多个助手分别写入不同部分，正式数据的生成或写入，权限或外部系统，或者明确要求独立验收时，使用本 Skill 中更严格的流程。向用户说明时称为“加强协作”，并直接说明会增加一次 Plan 检查和一次结果检查，不要求用户理解“受控协作”这个内部名称。

轻量协作中如果出现上述受控条件，停止受影响的部分，提交受控 Plan 重新确认；不得直接在轻量协作中加入 Canary、运行目录、`FINAL.md` 或完整审核流程。

一个 Agent 能低成本完成的多来源查询、简单解释、单文件读取和小修直接完成；拿不准分工是否有帮助时先不分工，发现确实需要多个 Agent 或风险上升后再升级。

已经确定需要多个 Agent，但因为缺少关键信息而无法判断采用轻量还是受控协作时，先询问具体事实，例如是否修改正式数据、涉及对外发布、难以回退或需要独立验收。只有两种方式都合理时，才向用户说明普通分工与加强协作分别会做什么，再请用户选择；不要只问“是否启用受控协作”。

受控协作的每个获批 Plan 必须记录：

- `delegate_agent`：用户指定、按子任务职责选择的合适专业 Agent，或 `current-agent`。
- `plan_reviewer_agent`：按同一规则选择的 Plan 审查角色；必须使用独立新 thread 和 `read` 权限。
- `result_reviewer_agent`：按同一规则选择的结果审核角色；必须独立于执行者，使用新 thread 和 `read` 权限。
- `run_root`（仅在下面规定需要单独工作目录时）：用户授权工作区中的运行根目录，默认 `<user-authorized-workspace>/runs/`。

用户明确指定 Agent 时优先使用；否则根据子任务职责选择合适的专业 Agent。没有合适角色时，继承当前 Agent 角色创建临时子 Agent。用户指定的 Agent 不可用时停止并报告，不静默替换。

轻量协作只需给子 Agent 一份包含必要背景的简短任务说明，不加载完整任务包和角色协议。受控协作执行前按顺序读取：

1. 先读 [任务包模板](references/task-packets.md)。
2. 再读对应角色协议：[执行协议](references/execution-protocol.md)、[研究协议](references/research-protocol.md) 或 [验证协议](references/validation-protocol.md)。
3. 需要汇报、请求决定或重新确认前，必须读完整的 [沟通协议](references/communication-protocol.md)。

受控协作无法加载沟通协议时，停止受影响的工作并报告 `BLOCKED`；只允许保持停止状态、保存已有进度并报告加载失败，不得只凭主文件摘要继续恢复、返修、正式执行或交付。

## 核心规则

1. **主代理负责**：主代理规划、综合并最终验收；子代理不拥有最终回复，不创建下级代理。
2. **开始前确认**：单步、明确且小范围的任务可以直接执行。普通多步骤任务和轻量协作提交简短的“步骤 → 验证”计划，获得用户确认后执行，不需要独立 Plan 审查。受控协作提交六段决策 Plan，同时完成独立审查和用户确认后执行；具体条件见“什么时候使用，以及如何加载规则”。
3. **选择 Agent**：用户明确指定 Agent 时优先使用；否则根据每部分工作的需要选择合适的专业 Agent。没有合适角色时，继承当前 Agent 角色创建临时子 Agent。新建专业 Agent 时传入所选身份；使用当前角色时省略 `agent` / `agentType`。默认继承所选角色的配置模型；只有用户明确批准时才覆盖。Agent 不可用时停止并报告。
4. **不同角色使用不同 thread**：Plan 审查、研究、执行和验证是不同角色，应分别使用新的 thread。只有继续处理原来分配给同一角色的工作时才使用原 `threadId`；同一 thread 不更换 Agent。
5. **只给必要权限**：研究、验证和 Plan 审查默认使用 `read`；写权限只给明确负责写入的人。选择身份或模型不得放宽权限、安全和验收要求。
6. **同一部分只交给一个执行者**：委派后由主代理负责协调，不与子代理重复工作；受控协作中，已有工作的普通补充查询记入 `QUERY_BACKLOG`。
7. **必要时先做最小试运行（Canary）**：轻量协作不因为使用了子 Agent 就自动做 Canary。受控协作中，如果调用涉及批量正式执行、写入、返回结构或权限不确定、成本较高，或者失败会明显影响数据和交付，先在同一子线程做一次最小试运行；低成本、只读、返回结构已知且结果可以直接核对的单次调用可以直接执行。Canary 失败时停止受影响的部分，不自行更换来源、扩大权限或降低结果可靠性。
8. **把长资料和验证依据保存到文件**：长数据、日志和表格写入文件；主上下文只保留状态、路径、关键发现、冲突和缺口。重要事实单独核对，关键数字使用可以重复检查的方法，结果能够从原始输入重新生成。
9. **什么时候使用单独工作目录**：受控协作需要多个助手分别写入不同部分、批量或正式数据落盘、保留可以独立重跑的依据，或者把中间文件与最终交付分开时，使用 `<run_root>/<time>-<slug>-<suffix>/`；不同写入部分使用互不重叠的目录。单一写入者在 clean、已获授权的 Git 工作区或用户指定目录内完成普通源码、文档、报告、演示文稿、表格或网页时，不另建运行目录。只读研究和直接对话回答也不使用运行目录。发现其他写入者、目录归属不明或写入范围重叠时立即停止，不自行合并或覆盖。
10. **什么时候创建 `FINAL.md`**：只有任务需要以后继续、跨会话恢复、汇总多个产物，或用户明确要求正式证据包时，才创建 `FINAL.md`。使用运行目录本身不代表必须创建 FINAL；如果运行目录只保存临时数据或隔离过程文件，而且最终结果单一明确，可以不创建。需要 FINAL 时，由主代理在总任务根目录或用户指定的正式交付根目录维护唯一文件；子代理不分别创建。普通 Git 修改、单一文件交付、只读研究和直接对话回答不创建 FINAL。FINAL 只记录证据和状态，不能代替真实验证、用户批准或外部发布授权。
11. **汇报不等于请示**：状态汇报不等于征求批准；“批准后持续执行”也不等于可以静默执行。子代理遇到关键异常时必须让用户知道，最接近用户的主代理负最终通知责任。
12. **规则冲突时停止**：本文件保留不能绕过的安全底线；各协议完整说明受控协作中的具体做法。规则冲突时先停止并修正规则，不能挑选更宽松的解释。

这些规则依靠 Agent 遵守；如果宿主没有相应的硬限制，就不能把它们说成系统强制的安全措施。

## 受控协作开始前的两项确认

受控协作开始前，既要得到用户确认，也要由另一名助手独立检查 Plan。向用户说明时直接说：“我建议采用加强协作：先由另一名助手检查计划，完成后再独立检查结果。”同时说明触发原因。轻量协作不进入本节。

1. 主代理形成 `PLAN_DRAFT`，同轮按身份路由规则派出 `read`、Plan 审查角色、独立新 thread 的审查者，并向 approver 展示六段 Plan。
2. 进入 `PLAN_REVIEWING` 后仅审查者可运行，不派研究、数据或执行任务。
3. approver 反馈与审查结果必须两方齐全；无回复不等于批准，不设超时默许。
4. “好的、开始执行、按这个计划做、没问题”等明确表述可视为批准。
5. 主代理裁决审查意见，approver 决定优先；冲突时列出并由 approver 裁决。
6. 不影响范围、方向、风险或交付目标的补充可以修订后执行，不再审查；这些方面出现实质变化时必须重新确认，但不会因此自动允许再次审核。只有 approver 明确同意额外审核时才能再次审核。
7. 审查后立即关闭 reviewer thread；后续研究、执行、验证使用各自新 thread。简单任务不触发此审查。

## 如何分工

- **A 直接完成**：一个 Agent 能低成本完成，或者分工没有实际作用。
- **B 轻量研究协作**：不同研究者分别查询不同方向的资料，负责解释或从相反角度检查，不重复获取同一批资料。
- **C 受控数据执行**：由一个有 `write` 权限的执行者正式获取和整理数据；根据风险决定直接执行，还是先做 Canary。其他研究者读取同一份数据。
- **D 受控研究协作**：几个不同研究方向需要使用相同定义和计算方式，最后统一汇总或独立验收。
- **E 受控一般执行**：目标和边界明确，按执行协议产出文件或代码。
- **F 受控分阶段执行**：明确关键定义 → 一次取数 → 分头分析 → 汇总 → 执行 → 验证 → 验收；只按实际依赖推进，不机械地走完所有步骤。

轻量协作给每个子 Agent 一份包含必要背景的简短说明，写明目标、负责的部分、可以使用哪些来源、需要返回什么以及做到哪里停止。受控协作先写清每个助手负责什么，再准备完整任务说明；子代理看不到主会话。只有几项工作互不依赖、使用相同定义，而且不会修改同一批文件时，才能并行。继续原来分配给同一角色的工作时优先使用原 `threadId`；续派沿用已经绑定的身份，不跨角色复用 thread；出现新的独立方向时才另派。等待期间，主代理只处理汇总框架、验收、冲突和关键定义。只有遇到关键阻塞、来源冲突、关键事实需要核对，或者用户明确要求时，主代理才做必要的有限查询，并提前写清查询用途和停止条件。验收前关闭不再需要的实例。

## 受控协作中什么时候汇报和暂停

轻量协作使用平台通常的状态与失败反馈，不使用下面这套完整沟通流程。

| 事件 | 触发摘要 | 动作摘要 |
|---|---|---|
| `STATUS_REPORT` | 关键阶段、重要发现、可安全恢复的异常 | 报告后继续，不等待 |
| `DECISION_REQUEST` | 分支会影响目标、成本、可信度、风险或不可逆动作 | 暂停相关分支等待 approver；无依赖工作可继续 |
| `REAPPROVAL_REQUIRED` | 范围、方向、风险、交付目标、权限或外部影响实质变化 | 暂停受影响执行并提交修订 Plan |

`FAILED / BLOCKED / NEEDS_REVISION` 只是状态，不一定都要停下来等待批准。只有局部、可逆、低成本，而且不换来源、不改变关键定义、不扩大权限、不降低结果可靠性的故障，才允许自行恢复一次；同一错误再次出现、执行者整体失败，或恢复会改变范围和结果可靠性时，必须报告，不能继续自行处理。完整状态、通知顺序、汇报节点、返回格式和失败处理见沟通协议。

## 验证、失败与交付

轻量协作由执行者检查自己负责的部分，主代理根据已批准范围和成功标准验收；验证通过后可以直接回复，不使用完整审核流程。

受控协作默认有两次独立检查：执行前检查一次 Plan，执行后检查一次结果。两次检查属于不同阶段，互不占用次数；每个阶段只检查一次，默认总数为两次。Plan 修订或结果返修后不再派审核助手，由主代理完成可以重复核对的检查和最终验收；只有用户明确同意时才能增加审核。

受控协作的结果审核使用 `DRAFT → VALIDATING → NEEDS_REVISION / ACCEPTED` 状态。验证结果返回并由主代理判断为 `ACCEPTED` 前，不得向用户宣布任务已经完成。这不影响阶段报告、事故通知、决策请求或重新审批；用户主动索要时，只提供明确标注的未验证草稿。

首次出现局部、可逆的错误时可以自行恢复一次。工具或权限不匹配时，必须停止受影响的部分并报告，只有未受影响的工作可以继续；同一错误连续出现两次、上下文超限、执行者整体失败，或者 Plan 和关键定义有错时，按沟通协议保存证据并说明以后如何继续。更换来源、扩大权限、降低结果可靠性或发生实质变化时，必须请求决定或重新审批。关键异常不得只写在内部日志或 FINAL 中。

受控协作只有结果审核达到 `ACCEPTED` 后才能发送最终完成回复；轻量协作在主代理确认成功标准满足后即可回复。任务存在 FINAL 时，回复必须与其中记录的正式产物和验证状态一致；没有 FINAL 时，以实际产物、可以重复核对的检查和已批准范围为准。结果审核受阻时明确说明：“产出已经生成，但验证还没有完成。”

## 修改本 Skill 时必须保持的行为

整理或审查本 Skill 时，不能为了缩短文字或删除重复而改变原有行为、规则优先级和安全要求。必须覆盖 [T01–T14 行为契约](references/behavior-contract.md)：受控协作开始前的两项确认、Agent 与 thread 选择、最小权限、Canary、QUERY_BACKLOG、运行目录、FINAL 和验证要求、汇报后继续安全工作、后台失败必须告诉用户、允许自行恢复的范围、NEEDS_REVISION、超出原范围后重新审批、正常加载沟通协议，以及协议加载失败时保持阻断。规则映射中测试 ID 为空时必须阻断；删除内容必须能指出仍由哪一处规则负责，并确认改写前后的行为相同。
